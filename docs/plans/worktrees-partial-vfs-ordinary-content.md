## Atomic C8 ingress

Use a dedicated ordinary adapter, leaving Provider EmptyIngress entry points
strict. The generic `copy_verified_prefix` already accepts genuine admitted B9
closure evidence and an actual private8 destination. It copies all thirteen v2
rowsets, including generation-zero snapshot/selection and restoration history.

Under the real owner, source snapshot and independently retained C pins:

1. Require exact SourceCopying, published FORMAT and Initializing membership.
2. Inspect the pinned C database; accept only Uninitialized or exact complete
   ordinary CopiedPrefix. Reject arbitrary partial EmptyIngress.
3. Obtain clean writer admission, retain geometry, enable FK and begin Immediate.
4. Create exact C8 schema, destination identity, ordinary backend and import
   prefix. Copy the genuine prefix rows before inserting DestinationCopying and
   head, because their generation-zero FK requires the copied snapshot to exist.
5. Set head to the outgoing prefix's source generation. Validate exact C8 schema,
   identity/backend/prefix, singleton destination intent, head and copied rows;
   every unrelated table remains empty.
6. Commit, positively close and independently read back the complete state.

Failure before successful COMMIT rolls back rather than committing an intermediate
EmptyIngress. A later close, cancellation or postvalidation failure can leave a
complete C8 copy durable; exact read-only replay must authenticate that state.
Replaying an exact complete copy performs no writes. Do not copy B's incoming
admission or outgoing intent rows as C history. Ancestry comes from the committed
import rowsets and receipts. Do not use B's current observation as C's G0.

The existing Provider `destination_validation::read_state` table exceptions
omit populated `projection_restore_history`. Any shared implementation must
retain exact restored-row commitment/count checks and permit them only at the
copied phase. A new ordinary reader must include them from its first version.

## Dedicated retained-B plus active-C family policy

The ReserveOnly integration has two coupled parts. Factor the complete
`AdmittedFamilyContext::validate_catalog` walk behind an optional active target,
leaving its ordinary entry point on the unchanged `None` path. Classify that
target only after checking all retained Published groups and required roots,
before the final all-reservation inventory. The export writer requires FK ON
and a caller transaction, with complete validation before and after its exact
insert/replay. Unknown groups and any C installation/root remain forbidden.

An export-only source callback must bootstrap from actual SourceStaging,
actual complete DestinationStaging, retained private mappings, cached canonical
manifests and the pinned current image. This DATA can nominate a ReserveOnly
target, but grants no physical content access. Under the dedicated validated
catalog gate, resolve historical/base representations by exact FileManifestId,
verify their indices and CAS bytes, then rederive the complete immutable plan,
Q/M and actual pair metadata floor before reservation. Current-image manifests
may legitimately not be installed yet; their bytes stay handle-backed.

Both ordinary lookups must be bypassed through this explicit export policy:
the pre-action `with_source_transaction` manifest read and the second manifest
read inside `derive_plan`. Otherwise an exact already-existing C reservation
prevents the retry from reaching its action. `Access::with_content`, scope
validation and readonly image scanning can retain their actual private/pin
checks; generic Lease and ContentScope authorization must not be widened.
Later retained file/chunk copying also needs the export-specific reader rather
than its present ordinary lease stream. This only covers the original owner's
retained access; reopening after owner/pin loss remains explicit recovery work.

Keep ordinary `Lease`, `ContentScope` and strict Provider wrappers unchanged.
Introduce an export-only context combining B's authenticated retained groups
with exactly one active target derived from actual B/C Staging rows, pinned C
FORMAT/database/owner, complete required manifests and validated metadata floor.
All fields remain private; detached descriptive inputs grant no physical access.

The validator must classify all retained groups and their Published debit
equality, plus only C's exact reservation/installation group. It must reject
unknown reservations, exact journals, C effects, legacy installations and
unrelated active targets. Validate C's exact Initializing registry, operation,
owner, quota, and absence of a protection root before the appropriate phase.

Three current fences need specialized interpretation, not removal:

- `OrdinarySourceInputs::require_family` uses strict retained admission and
  rejects an active unretained C reservation.
- `provider_import/content::validate_reservation_only` rejects every exact
  installation, including legitimate retained B rows.
- `exact_content/sql::validate_installations_inner` rejects other reservation IDs
  and enumerates all exact rows rather than just the active C group.

The Installing extension should use a closed alternative in the same complete
admitted catalog walk. Factor the active-group validation kernel from
`exact_content/sql.rs`, keeping the strict Provider wrapper unchanged. An
export-only `ExactBinding::validate_export_installations` receives the SAME
charged-chunk and charged-manifest sets populated by all retained Published
groups. It verifies C's actual journal phases, canonical projections, cursors,
inodes, indexed/resident pieces and exact remaining/debit equality. The final
all-reservation classification and global usage remain mandatory; filtering to
C without those checks would omit unknown or doubly charged groups.

Installing prospective journal capacity differs from ReserveOnly:
`global_records - current_C_records + complete_required_C <= 100000`.
Each C journal pays its own 8192-byte prepare charge and its own canonical
manifest column, even when physical CAS objects are already resident. Global
usage includes CAS chunks, CAS manifest payloads, sweep, every exact journal's
prepare/manifest metadata and all remaining reservations. Physical objects must
not be debited twice across retained and active groups.

There is also a Windows sharing adaptation before installing with retained CAS
pins. `open_file` requests DELETE; the immutable B object handles allow READ
sharing only. Existing CAS-only identity/read opens in exact-content `spool.rs`
and `publish.rs` must use `open_readonly_file`. Keep rename rights on staging
sources and keep the immutable B pins. This is a distinct physical adjustment,
not a reason to weaken the complete catalog validator or drop source protections.

The future ordinary Installing `ExactCatalog` adapter borrows actual B/C owners,
source image/closure, target and CAS pins. Its callback reauthenticates those
inputs and the full retained-plus-active catalog around each action; byte I/O
stays outside catalog scopes. Existing prepare/piece/finish/publish operations
can then be reused with current-image or exact retained byte producers. None of
this Installing work is implemented or qualified by the ReserveOnly slice.

Retain global inventory bounds and total family accounting. Share charged
manifest/chunk sets between retained and active groups so duplicated debit cannot
pass. A target WHERE clause alone is insufficient. ReserveOnly permits retained
B journals but no C progress; Installing admits only C's typed progress.
